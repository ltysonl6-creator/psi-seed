# Ψ-SEED CACC v0.10 — Authoritative State Projection + Complete Rollback Semantics

## Core rule

**Current state is a projection of authoritative revision history. A rollback may change the current projection, but it may never rewrite the history from which that projection is derived.**

## Changes

- `entity_revisions.status` is now authoritative and versioned alongside payload/provenance.
- `update_belief()` is now a versioned compatibility alias; unversioned belief mutation is removed.
- Self-modification status changes create revisions.
- Generic `revise_entity()` versions non-belief state mutations.
- Rollback restores payload, provenance, and status from one historical snapshot.
- Rollback records `target_state_digest`, compatibility `restored_state_digest`, and `result_state_digest`.
- `reconstruct_from_history()` ignores mutable entity payload/version/status and derives the current projection solely from the latest authoritative revision.
- Revision chains must be contiguous and complete.
- Optional CACC transition linkage creates a `transition_rollback` entity and `rollback_of_transition` relationship.
- Existing v0.9 SQLite databases receive an automatic `entity_revisions.status` migration. Historical status values from v0.9 are not authoritative because v0.9 did not version status; v0.10 makes status authoritative for all newly-created revisions.

## Explicit boundary

A rollback is not time travel. It creates a new revision whose state is equal to a prior revision's state while retaining every intervening revision, event, outcome, and causal record.

## Verification

The v0.10 suite contains 65 passing tests, including the prior CACC/state-rollback suite plus adversarial tests for mutable-projection poisoning, status rollback, digest correctness, unversioned mutation, incomplete revision state, replay, CACC graph linkage, immutable rollback targets, and atomic failure.
